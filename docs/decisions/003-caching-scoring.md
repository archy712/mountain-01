## 🔶#8 — 캐싱/갱신 주기 (TTL)

**결정: 소스별 실제 발표 주기에 맞춰 아래 TTL을 v1으로 동결한다.** TTL은 "새 발표를 놓치지 않는 선"에서 쿼터 낭비를 피하도록 발표 주기에 정렬했다.

### 캐시 키 · TTL 표

| 소스           | API                                   | 실제 발표 주기          | TTL(v1) | 캐시 키 구성                          |
| -------------- | ------------------------------------- | ----------------------- | ------- | ------------------------------------- |
| 날씨(당일 D-0) | 초단기실황 `getUltraSrtNcst`·초단기예보 | 매시각 발표             | **30분** | `weather:{mountainId}:{base_date}:{base_time}` |
| 날씨(익일↑)    | 단기예보 `getVilageFcst`              | 1일 8회(02·05·…·23시)   | **3시간** | `vilage:{mountainId}:{base_date}:{base_time}` |
| 대기질         | 에어코리아 `getCtprvnRltmMesureDnsty` | 1시간 단위              | **1시간** | `air:{stationName}:{yyyyMMddHH}`       |
| 자외선         | 생활기상지수 `getUVIdxV5`             | 1일 2회(06·18시)        | **3시간** | `uv:{areaNo}:{yyyyMMddHH}`             |
| 탐방로         | 국립공원공단 CSV(정적) + 오늘 통제 계산 | 정적 2023 스냅샷        | **6시간** | `trails:{mountainId}:{yyyyMMdd}`       |

- **근거:** 발표 주기보다 짧은 TTL은 동일 값을 재요청해 쿼터만 소모(대기질·자외선은 발표 주기에 정렬). 날씨(D-0)만 사용자 체감 신선도를 위해 발표(1시간)보다 짧은 30분으로 설정.
- **탐방로**는 라이브 호출이 없고 조회일(`yyyyMMdd`)이 바뀔 때만 통제 판정이 변하므로 6시간이면 충분(일 경계만 반영되면 됨).
- **stale 폴백:** 실패 시 마지막 성공 응답을 `fetchedAt`과 함께 반환하여 "N분 전 기준" 라벨 노출(Task 015).
- **재튜닝:** Task 032에서 캐시 히트율·응답시간 실측 후 조정. 일일 호출 한도(Task 001 잔여)를 확인해 TTL 하한 검증.

## 🔶#9 — 캐싱 구현 방식

**결정: 두 레이어의 역할을 분담한다.**

- **외부 API 정규화 응답 → Next `"use cache"` + `cacheLife`** (`next.config.ts`의 `cacheComponents: true` 전제)
  - 휘발성 캐시. 소스별 TTL(#8)을 `cacheLife` 프로필로 적용. 서버 프록시(`lib/api/*`)에서 일원화.
- **계산된 컨디션 점수 → Supabase `condition_scores` 테이블**
  - 지속성 캐시. `score`·`grade`·`breakdown`(jsonb)·`calc_version`·`computed_at` 저장.
  - `/favorites` 목록에서 저장 산의 최신 점수 요약을 재계산 없이 조회(2단계).
  - 조회 시 `calc_version`·`computed_at`으로 유효성 판단, 만료/버전 불일치 시 재계산.
- **경계:** 원천 데이터(날씨·대기·자외선) 캐싱은 Next 캐시 담당, "가공 결과(점수)의 버전 관리·공유·영속"은 테이블 담당. 이중 저장 아님.

## 🔶#10 — 점수 계산 위치 / 버전 관리

**결정: 점수는 서버에서만 계산하고 `calc_version`으로 태깅한다.**

- **위치:** `lib/condition/score.ts`(순수 함수) — Route Handler `GET /api/condition`에서 호출. **클라이언트 계산 금지**(입력 원천 데이터가 서버 프록시에만 있음).
- **`calc_version` 형식:** 문자열 `"v{정수}"` (예: `v1`). 초기값 `v1`.
- **증가 규칙:**
  - **가중치·구간·보간식·등급 경계 변경** → 버전 증가(`v1`→`v2`).
  - 버그 수정으로 결과가 달라지면 증가, 결과 불변 리팩터링은 유지.
- **캐시 상호작용:** `condition_scores`는 `(mountain_id, calc_version)` 기준으로 유효. **버전 변경 시 구버전 행은 무시하고 재계산**(무효화). 동일 입력+동일 버전 → 동일 점수(회귀 검증 대상, Task 027).

## 🔶#13 — PWA 캐싱 전략

**결정: 앱 셸은 precache(cache-first), 데이터는 network-first(캐시 폴백).**

- **앱 셸(정적 자원: HTML 셸·CSS·JS·아이콘·`/offline`)** → 설치 시 precache, **cache-first**. 서비스워커 버전 변경 시 구버전 캐시 정리.
- **데이터(API 응답·산 상세)** → **network-first**, 실패 시 마지막 조회 캐시 표시("N분 전 기준" 라벨 #8 재사용). 미보유 시 `/offline`.
- **구현 수단:** 로드맵대로 **손수 작성한 `public/sw.js`**(의존성 최소화, 앱 셸+런타임 캐시 분리). 유지보수 부담 커지면 Serwist(next-pwa 후속) 도입 재검토.
- **영향 Task:** Task 030(`app/manifest.ts`·`public/sw.js`·`/offline`).
